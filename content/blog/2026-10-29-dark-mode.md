Because my components only use [semantic tokens](./2026-10-27-design-tokens), dark mode didn't require changing any component. The whole change was in `tokens.css`.

## The old way

The usual approach is to write every token twice:

```css
:root {
	--text-1: var(--gray-8);
}
@media (prefers-color-scheme: dark) {
	:root {
		--text-1: var(--gray-1);
	}
}
```

It works, but each token's light and dark values end up far apart in the file. Adding a manual toggle on top means writing the dark values a third time.

## color-scheme + light-dark()

```css
:root {
	color-scheme: light dark;

	--brand: light-dark(var(--blue-9), var(--blue-4));
	--text-1: light-dark(var(--gray-8), var(--gray-1));
	--surface-1: light-dark(var(--gray-0), var(--gray-11));
}

:root[data-theme='light'] {
	color-scheme: light;
}
:root[data-theme='dark'] {
	color-scheme: dark;
}
```

- **`color-scheme: light dark`** tells the browser the page supports both themes and should follow the OS. It also switches the browser's own UI, such as scrollbars, form controls and the default background.
- **`light-dark(a, b)`** returns `a` in a light color scheme and `b` in a dark one. Each token keeps both of its values on one line.
- **`[data-theme]`** forces a theme. With no attribute the site follows the OS. A toggle just sets the attribute on `<html>`.

The dark values are the same scales flipped. The brand color moves from `--blue-9` to `--blue-4`, because a dark blue is unreadable on a dark background.

## What the build did

The built CSS doesn't contain `light-dark()`. Lightning CSS, Vite's minifier, replaced it with a fallback for older browsers: two switch variables and a generated `@media (prefers-color-scheme: dark)` block. My `[data-theme]` selectors are more specific than that generated `:root`, so a forced theme still wins over the OS. I write the modern syntax and the build handles older browsers.

## Testing

In DevTools, open the command menu (Ctrl+Shift+P), run **"Emulate CSS prefers-color-scheme: dark"**, then add `data-theme="light"` to `<html>` in the Elements panel. The page should go back to light even though the OS emulation is still dark.

## Avoiding the flash

Saving the choice is easy. Applying it at the right moment is the hard part.

My site is prerendered, so the HTML is generated at build time, when there's no visitor and no `localStorage`. The browser paints that HTML first, without any `data-theme`, so it shows the OS theme. Then SvelteKit's JavaScript loads, reads the saved choice, and switches. If you picked dark on a light OS, you'd see a white page flash on every load.

The fix is a small inline script at the top of `app.html`:

```html
<script>
	try {
		const theme = localStorage.getItem('theme');
		if (theme === 'light' || theme === 'dark') document.documentElement.dataset.theme = theme;
	} catch {}
</script>
```

- **A plain inline `<script>` in `<head>` blocks parsing.** The browser runs it before it reaches `<body>`, so the attribute is set before anything is painted. SvelteKit's own scripts are modules, which run after parsing, and that's too late.
- **It validates the value.** `localStorage` is data from outside your code, and anyone can put `banana` in it.
- **The `try` is there because `localStorage` can throw** when storage is blocked. If it throws, the site just follows the OS.

## The toggle

```svelte
<script lang="ts">
	import { onMount } from 'svelte';

	type Theme = 'light' | 'dark';

	let theme = $state<Theme>();

	onMount(() => {
		const saved = document.documentElement.dataset.theme;
		theme =
			saved === 'light' || saved === 'dark'
				? saved
				: matchMedia('(prefers-color-scheme: dark)').matches
					? 'dark'
					: 'light';
	});

	function toggle() {
		theme = theme === 'dark' ? 'light' : 'dark';
		document.documentElement.dataset.theme = theme;
		try {
			localStorage.setItem('theme', theme);
		} catch {}
	}
</script>

<button type="button" onclick={toggle} aria-pressed={theme === 'dark'} disabled={!theme}>
	Dark theme
</button>
```

- **`theme` starts as `undefined`.** During prerendering nobody knows the visitor's theme. If it started as `'light'`, the HTML would contain `aria-pressed="false"` even for visitors whose OS is dark. The button stays disabled until `onMount`, which only runs in the browser.
- **The inline script decides the colors. `onMount` only syncs the button** with the attribute the script already set, or with the OS setting if there's no saved choice.
- **`toggle()` does three things:** it updates the state (for the button), sets the attribute (which the CSS reacts to), and saves the choice (for the next visit).

### A fixed label with `aria-pressed`

The button always says "Dark theme", and `aria-pressed` tells screen readers whether it's on. A label that flips between "Light" and "Dark" is ambiguous: does it describe the current theme or what happens when you click? This matters for more people than you might think. Many screen reader users have low vision and do care about themes, and voice control users click buttons by saying their label.

### Two states or three?

There was a lively debate about this in 2026. [Lea Verou argues](https://lea.verou.me/blog/2026/dark-mode-toggles/) that a visible toggle only needs two states, and [later](https://lea.verou.me/blog/2026/dark-mode-toggles-2/) that most sites don't need one at all. [Bramus makes the case](https://www.bram.us/2026/08/18/the-case-for-tri-state-dark-mode-toggles/) for showing all three (system, light, dark). And [Kilian Valkhof's older post](https://kilianvalkhof.com/2020/design/your-dark-mode-toggle-is-broken/) points out that a toggle with no way back to "system" is broken.

I went with one button. If the site ever gets a settings panel, "Use system setting" will go there. For now, the trade-off is that once you click, your choice overrides the OS until you clear storage.
