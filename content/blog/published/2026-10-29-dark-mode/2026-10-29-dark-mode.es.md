Como mis componentes solo usan [tokens semánticos](./2026-10-27-design-tokens), el modo oscuro no obligó a cambiar ningún componente. Todo el cambio fue en `tokens.css`.

## La forma de antes

Lo habitual es escribir cada token dos veces:

```css
:root {
	--text-1: var(--gray-8);
}
@media (prefers-color-scheme: dark) {
	:root {
		--text-1: var(--gray-1);
	}
}
```

Funciona, pero los valores claro y oscuro de cada token acaban lejos el uno del otro en el archivo. Añadir encima un selector manual significa escribir los valores oscuros una tercera vez.

## color-scheme + light-dark()

```css
:root {
	color-scheme: light dark;

	--brand: light-dark(var(--blue-9), var(--blue-4));
	--text-1: light-dark(var(--gray-9), var(--gray-1));
	--surface-1: light-dark(var(--gray-0), var(--gray-11));
}

:root[data-theme='light'] {
	color-scheme: light;
}
:root[data-theme='dark'] {
	color-scheme: dark;
}
```

- **`color-scheme: light dark`** le dice al navegador que la página admite los dos temas y que debe seguir al sistema operativo. También cambia la propia interfaz del navegador, como las barras de desplazamiento, los controles de formulario y el fondo por defecto.
- **`light-dark(a, b)`** devuelve `a` con un esquema de color claro y `b` con uno oscuro. Cada token tiene sus dos valores en una sola línea.
- **`[data-theme]`** fuerza un tema. Sin el atributo, el sitio sigue al sistema operativo. Un selector solo tiene que poner el atributo en `<html>`. (Más adelante estos selectores perdieron su `:root`, y los tokens se declaran en cualquier elemento con `[data-theme]`, para que también una parte de una página pueda forzar un tema. El artículo de mi comprobador de contraste cuenta por qué.)

Los valores oscuros son las mismas escalas al revés. El color de marca pasa de `--blue-9` a `--blue-4`, porque un azul oscuro no se puede leer sobre un fondo oscuro.

## Qué hizo el build

El CSS generado no contiene `light-dark()`. Lightning CSS, el minificador de Vite, lo sustituyó por una alternativa para navegadores antiguos: dos variables interruptor y un bloque `@media (prefers-color-scheme: dark)` generado. Mis selectores `[data-theme]` son más específicos que ese `:root` generado, así que un tema forzado sigue ganando al del sistema. Yo escribo la sintaxis moderna y el build se ocupa de los navegadores antiguos.

## Probarlo

En DevTools, abre el menú de comandos (Ctrl+Mayús+P), ejecuta **"Emulate CSS prefers-color-scheme: dark"** y luego añade `data-theme="light"` a `<html>` en el panel Elements. La página debería volver a claro aunque la emulación del sistema siga en oscuro.

## Evitar el parpadeo

Guardar la elección es fácil. Lo difícil es aplicarla en el momento justo.

Mi sitio está prerenderizado, así que el HTML se genera al construir el sitio, cuando no hay ningún visitante ni `localStorage`. El navegador pinta primero ese HTML, sin ningún `data-theme`, así que muestra el tema del sistema. Luego carga el JavaScript de SvelteKit, lee la elección guardada y cambia. Si elegiste oscuro con un sistema en claro, verías una página blanca parpadear en cada carga.

La solución es un pequeño script en línea al principio de `app.html`:

```html
<script>
	try {
		const theme = localStorage.getItem('theme');
		if (theme === 'light' || theme === 'dark') document.documentElement.dataset.theme = theme;
	} catch {}
</script>
```

- **Un `<script>` normal en línea dentro de `<head>` bloquea el análisis.** El navegador lo ejecuta antes de llegar a `<body>`, así que el atributo está puesto antes de pintar nada. Los scripts de SvelteKit son módulos, que se ejecutan después del análisis, y eso es demasiado tarde.
- **Valida el valor.** `localStorage` son datos de fuera de tu código, y cualquiera puede meter `banana` en él.
- **El `try` está porque `localStorage` puede lanzar un error** cuando el almacenamiento está bloqueado. Si lo lanza, el sitio simplemente sigue al sistema operativo.

## El selector

```svelte
<script lang="ts">
	import { onMount } from 'svelte';

	type Theme = 'light' | 'dark';

	let theme = $state<Theme>();

	const systemTheme = (): Theme =>
		matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light';

	onMount(() => {
		const sync = () => {
			const saved = document.documentElement.dataset.theme;
			theme = saved === 'light' || saved === 'dark' ? saved : systemTheme();
		};
		sync();

		const query = matchMedia('(prefers-color-scheme: dark)');
		query.addEventListener('change', sync);
		return () => query.removeEventListener('change', sync);
	});

	function toggle() {
		theme = theme === 'dark' ? 'light' : 'dark';
		const root = document.documentElement;
		try {
			if (theme === systemTheme()) {
				delete root.dataset.theme;
				localStorage.removeItem('theme');
			} else {
				root.dataset.theme = theme;
				localStorage.setItem('theme', theme);
			}
		} catch {}
	}
</script>

<button
	type="button"
	onclick={toggle}
	aria-pressed={theme ? theme === 'dark' : undefined}
	disabled={!theme}
>
	Dark theme
</button>
```

- **`theme` empieza en `undefined`.** Durante el prerenderizado nadie sabe el tema del visitante, así que el HTML no debe afirmar ninguno. Por eso `aria-pressed` es `undefined` hasta entonces: Svelte pinta `false` en un atributo `aria-*` como el texto `"false"`, que les diría a quienes tienen el sistema en oscuro que el tema oscuro está desactivado. Solo `undefined` deja fuera el atributo. El botón sigue desactivado hasta `onMount`, que solo se ejecuta en el navegador.
- **El script en línea decide los colores. `onMount` solo sincroniza el botón** con el atributo que ya puso el script, o con la preferencia del sistema si no hay ninguna elección guardada. El listener de `change` lo vuelve a sincronizar si el tema del sistema cambia con la página abierta, y `onMount` devuelve una función de limpieza que quita el listener.
- **`toggle()` guarda una preferencia propia o la quita.** Si el tema nuevo es distinto del del sistema, pone el atributo y lo guarda. Si coincide con el del sistema, borra los dos, así que el sitio vuelve a seguir al sistema. Más sobre esto abajo.

### Una etiqueta fija con `aria-pressed`

El botón siempre dice "Dark theme", y `aria-pressed` les dice a los lectores de pantalla si está activado. Una etiqueta que cambia entre "Claro" y "Oscuro" es ambigua: ¿describe el tema actual o lo que pasará al hacer clic? Esto le importa a más gente de la que parece. Muchas personas que usan lector de pantalla tienen baja visión y sí les importan los temas, y quien usa control por voz pulsa los botones diciendo su etiqueta.

Más adelante el botón se convirtió en un icono animado de sol y luna (mira [el artículo siguiente](./2026-10-30-theme-toggle-view-transition)). La etiqueta fija se quedó: pasó a `aria-label="Dark theme"`, más un `title` para que quien usa el ratón la vea como descripción emergente.

### ¿Dos estados o tres?

En 2026 hubo un debate animado sobre esto. [Lea Verou defiende](https://lea.verou.me/blog/2026/dark-mode-toggles/) que un selector visible solo necesita dos estados, y [más tarde](https://lea.verou.me/blog/2026/dark-mode-toggles-2/) que la mayoría de los sitios no necesitan ninguno. [Bramus defiende](https://www.bram.us/2026/08/18/the-case-for-tri-state-dark-mode-toggles/) mostrar los tres (sistema, claro, oscuro). Y [un artículo más antiguo de Kilian Valkhof](https://kilianvalkhof.com/2020/design/your-dark-mode-toggle-is-broken/) señala que un selector sin forma de volver a "sistema" está roto.

Me quedé con el modelo de Lea. Hay un solo botón, y sus dos estados son **el tema del sistema y su contrario**. El modelo de fondo sigue teniendo tres estados (sistema, claro, oscuro), pero nadie tiene que elegir "sistema" explícitamente. Cuando vuelves con un clic al tema que coincide con tu sistema, el selector borra la preferencia en vez de guardarla, y el sitio vuelve a seguir al sistema. Si algún día el sitio tiene un panel de ajustes, ahí puede ir una opción explícita de "Usar la preferencia del sistema".
